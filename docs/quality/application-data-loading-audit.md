# Application Data-Loading Audit

## Scope and evidence

This audit inventories the pages registered in `apps/web/src/routes/AppRoutes.jsx` and traces their frontend service calls to API mounts and role-protected route handlers. Runtime checks are being performed against the authorized local development session using GET-only requests. No database writes/DDL, migrations, provider requests, or notification/export-generation actions are performed.

Read-only runtime passes are complete for all 11 Worker routes, all 11 Fund Manager routes, all 10 Regulator routes, and all 13 Admin routes. Actual response counts and visible page states are recorded below; personal and financial values are intentionally omitted. Runtime checks used the existing manually authenticated sessions and GET requests only. Mutating workflows and public authentication submissions were not exercised.

`useApi` sets and clears loading state, preserves an error in hook state, and exposes retry; the reviewed data pages render an error rather than treating failed first loads as empty results. Empty collections are rendered as empty states. Some pages preserve previously loaded data while showing a refresh error, which is intentional stale-data behavior.

## Data-loading problems and corrections

All 54 registered frontend paths are listed above. The 45 role-specific pages (11 Worker, 11 Fund Manager, 10 Regulator, and 13 Admin) were loaded in their existing authorized browser sessions and checked against observed GET responses and visible UI. Frontend API service paths were matched against the API mounts in `apps/api/src/server.js` and their route declarations. Existing route middleware provides role checks for worker-owned data, manager/regulator operational data, and admin-only management data; this work did not weaken or bypass those checks. Cross-role access attempts and mutating workflows were not performed.

The development admin self-test path had a persistence-boundary defect: if the provider returned acceptance but persisting that outcome failed, the broad `try/catch` treated the persistence exception as if the provider request had an ambiguous outcome. The send call is now isolated from the outcome-persistence step. Persistence failure is surfaced through the existing safe server-error path; it is not falsely recorded as provider `UNKNOWN` or retried. A mocked regression test asserts this behavior and verifies the provider is called only once.

The Fund Manager runtime pass confirmed empty datasets on three pages and a missing report-history relation on two pages. It also exposed malformed SQL in the notification audit query; this source bug is corrected and covered by the focused mocked test, but the currently running API has not been reloaded, so a successful live retest is still outstanding. The notification recipients endpoint also returned a generic 500; the API intentionally omits raw database errors, so its exact backend cause cannot be established from the permitted response alone.

The Regulator runtime pass covered all 10 registered pages. The audit-log page returned an empty list and the profile loaded. Scoped funds, compliance, notification, and report APIs returned errors; report scope, analytics, and history returned SQLSTATE `42P01`. The report/dashboard error-versus-empty display defect was corrected and verified in the live frontend: when report loading fails, the page now shows only retryable errors, not misleading empty states.

The Worker runtime pass covered all 11 registered pages. Balance, contribution, fund, retirement, literacy, and profile data rendered from successful GET requests. Withdrawal eligibility loaded and the claims list correctly showed no records. The personal notification GET returned HTTP 500 and the page showed a retryable error; its sanitized response does not reveal the underlying cause. The Worker dashboard and analytics rendered without load errors; the no-completed-contributions message was not treated as an API failure.

The exception is the newly requested external-recipient SMS capability on `/admin/notifications`: its existing notification schema could not safely represent a non-account recipient. The page now reports availability from an admin-only API; the sending endpoint stays unavailable unless `MOBILESASA_EXTERNAL_RECIPIENTS_ENABLED=true`, production Mobile Sasa SMS is configured, and the proposed migration has been applied. The migration is not applied in this task, so sending cannot be used against an unchanged schema. This is a known `DATABASE/MIGRATION REQUIRED` state, not an empty notification list or an assumed service failure. External rows use a null recipient `user_id`; recipient, consent time, and delivery evidence live on that row, with the immutable audit event linked by notification ID. They remain compatible with Mobile Sasa delivery-report correlation and are excluded from the general dispatcher. Existing registered-recipient notification history and audit queries do not require the new schema.

## Outstanding verification

- The Worker notification endpoint and the manager/regulator/admin notification recipient and audit endpoints still need backend investigation. The malformed notification-audit SQL correction is covered by a mocked regression test but was not reloaded and verified in the live API process.
- The public authentication forms and protected change-password workflow were not submitted, because those operations would mutate account/authentication state. They remain source-inventoried but not runtime-verified.
- Cross-role forbidden requests were not attempted. Role enforcement was inspected in route middleware; this audit does not claim runtime verification of cross-role denial.
- Browser console output included transient 401 responses during manual role transitions; these were not attributed to a stable page. The listed 500 responses corresponded to visible page-level error states.
- Reload the API and re-check `/api/notifications/audit` and `/api/notifications/recipients` through the Manager UI; do not infer success from the source correction alone.
- The report-history endpoint returns PostgreSQL SQLSTATE `42P01`; `database/migration_role_notifications_and_reporting.sql` defines `report_generation_history` and `regulator_fund_assignments`. Regulator-scoped endpoint source queries also require `regulator_fund_assignments`, while compliance review queries use `compliance_report_submissions` and `compliance_report_reviews` from `database/migration_compliance_review_workflow.sql`. API error responses for some of these endpoints are sanitized and do not reveal which missing relation failed first. Do not execute migrations within this audit.
- Confirm applied migration history and actual role/fund scopes only through an authorized, read-only view. No provider, email, SMS, push, payment, generation, or mutation request was made.
- After successful migrations in a separately authorized deployment process, rerun affected GET pages to establish whether they display records or empty states.
